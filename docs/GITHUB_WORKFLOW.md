# GitHub 迭代与仓库规范

## 目录约定

```text
README.md                         项目入口与启动说明
CHANGELOG.md                      已发布版本与未发布变更
docs/
  ROADMAP.md                      产品路线图
  GITHUB_WORKFLOW.md               协作与归档规则
  versions/                       已交付版本档案
  iterations/                     各版本迭代计划
  ui/v0.2.0/                      UI 设计说明与截图（按需建立）
  acceptance/v0.2.0/              验收记录（按需建立）
.github/
  ISSUE_TEMPLATE/                 需求和缺陷模板
  pull_request_template.md        PR 验证要求
Instrument_tool/Instrument_tool/  保留现有业务目录
```

不为每个版本复制整套源码。源码历史由提交和标签保存；计划与验收记录按版本分目录。运行日志、录像和大型交付包不作为普通源码文档提交；交付包放 Release，归档材料需移除 VIN、设备标识等无关敏感信息。

## GitHub 对象结构

建议建立一个 Project：**仪表工具产品迭代**，持续服务所有版本。

- 状态：待整理 → 已排期 → 开发中 → 待验收 → 已完成；增加“阻塞”字段记录原因。
- 字段：目标版本、优先级、类型、模块、负责人。
- 视图：当前迭代看板、按版本分组表、UI 需求、功能需求。
- Milestone：每个确定版本一个，如 `V0.2.0 UI 样板升级`；候选需求不设置截止日。
- 标签：`type:ui`、`type:feature`、`type:bug`、`type:docs`；`priority:P0/P1/P2`；`module:仪表/车控/QNX/公共界面`（分别建立对应标签）。

本文件是配置规范，不表示远端 Project、Milestone 或标签已创建。

## 工作流程

1. Issue 写清问题/目标、范围和可验收条件，UI 附当前图与目标图，功能写清设备前提。
2. 排入目标 Milestone，在迭代计划中填写真实 Issue 链接。
3. 从 main 建短期分支：`ui/<issue>-<主题>`、`feat/<issue>-<主题>`、`fix/<issue>-<主题>`、`docs/<主题>`。
4. 每个 PR 聚焦一个可独立验收的修改；正文关联 Issue，记录验证证据。
5. UI 检查布局、缩放、截图和原功能入口；功能检查输入、结果、失败路径及对应实机行为。
6. 验收通过后合并 main，更新计划和 CHANGELOG。单人维护可自行审阅，团队开发安排其他维护者审阅。
7. 版本范围完成后发布标签和 Release，更新版本档案。

main 为持续集成主线，已交付版本通过标签保留。暂不设长期 develop；只有同时维护旧版确有需要时再建立 release/0.1。

## 发布与归档

- 版本采用 `v0.1.0`、`v0.1.1`、`v0.2.0`：修复递增补丁号，UI/功能迭代递增次版本号。
- 首次归档先确认基线提交。已识别的当前代码提交为 `ca50a6b`；打标签前核实它与实际交付代码一致。
- 在选定提交创建标签；Release 标题与标签一致，附变更摘要、交付包、运行环境、兼容范围、已知限制及验收记录链接。
- 不把未执行的实机检查写成已通过；代码检查和设备验收分开记录。
- 已发布标签不移动；问题通过新提交和补丁版本修复。保留上一稳定版交付包以便回退。
- 建议 main 要求 PR 和适当自动检查；具体保护规则按账户能力和团队人数配置，不阻断单人维护。

## 完成条件

Issue 的验收条件满足、PR 有验证记录、文档同步。涉及设备但未实测的任务保留“待验收”，或明确拆分已完成代码任务与未完成设备验收任务。
